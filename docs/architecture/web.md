# Web

The Phoenix layer: each screen and controller, the router and the authentication hooks, the account pages, the app shell, the components and assets, and roles. `README.md` has the domain model and the map of the architecture files.

## Layer 4: Web — Phoenix LiveView Chat Interface

**`CakeWeb.ChatLive`** is the user-facing chat UI. It starts a `Conversation` GenServer and subscribes to its PubSub topic for state-change, candidates-ready, response-ready, and error broadcasts. The conversation's lifetime is the page's: ChatLive starts it as `:owner`, so it stops when the LiveView exits, and monitors it the other way round. If the conversation dies first, the page survives: it apologises, keeps the message history, disables the question form, and offers a "Start a new conversation" action that starts a fresh `Conversation` with no memory of the earlier turns (restoring that state is #39). One window remains in which an auto-mode question can be lost to a conversation that dies between ChatLive's liveness check and the cast, because `autoask/2` does not acknowledge acceptance (#311); the comments on `dispatch_question/3` have the detail. Domain-level candidate grouping and chunk-ID extraction are delegated to **`Cake.Candidates`** (a top-level boundary of its own, see "Module Boundaries" in `docs/architecture/inventories.md`): it groups candidates by document id (the `Cake.Citable` `source_ref`, or the `id` of a unit with none), summarises a group for display — a title, a 100-character preview and a page label that counts distinct pages, so several chunks on page 5 read "PDF page 5" — and expands a selection of documents back into candidate ids (`all_chunk_ids/1`, behind "Use all", is every candidate's id). Two embedded-schema form modules live under `chat_live/`: **`QuestionForm`** (question + mode validation) and **`SelectionForm`** (document-selection validation with subset checking against available IDs).

**`CakeWeb.UploadLive`** is the book-upload UI: accepts PDF and ZIP uploads (ZIP archives are unpacked to PDFs via `Cake.Books.ZipExtractor`), writes the files through the configured `Cake.Books.Adapters` storage adapter, then runs `Cake.Books.Pipeline.ingest/4` with `Cake.Books.Pdf.Pipeline` as an async task. The upload limits (20 files, PDF or ZIP, through the drop zone and 200 PDFs through the folder option, each file up to 100 MB) bound compressed bytes only; `Cake.Books.ZipExtractor` bounds expansion, before and during inflation, by `:max_zip_entries` and `:max_zip_expanded_bytes` (its moduledoc says how, and why it reads the archive's directory itself). `UploadLive` reports a rejected archive with the limit it broke: as the page's error when nothing else in the batch can be ingested (that error names only the first rejected archive), otherwise in a warning listing each rejected archive while the rest of the batch is ingested. Indexed is not yet searchable: the collection takes in new documents every 30 seconds (`index.refresh_interval`, see `Cake.Search.Deployment` in `docs/architecture/search.md`), so a question asked or a search run sooner than that after the notice can find nothing, and nothing on this screen or in the chat says so (#410). A storage write that fails crashes the LiveView instead of being reported (#292).

**`CakeWeb.SearchLive`** is a direct search UI at `/search`: it embeds the query itself (`Cake.Embeddings` with `:default_provider` and `:default_embedding_model`), runs `Cake.Search.search_chunks_with_context/5` against the `Cake.Books.ParsedBook` GDS, which it hardcodes, and renders the grouped results without starting a conversation.

**`CakeWeb.ParsedBookLive.Index`** is the documents list at `/documents`: a read-only table of what has been uploaded, newest first (`Cake.Books.list_parsed_books_newest_first/0`, which returns a map of the six fields the list shows for each book, not a `ParsedBook`). The module keeps the name `mix phx.gen.live` gave it; to a user the screen is "Documents". The list is read when the page opens and again when the Refresh button is pressed, and the page says when it was last read: nothing announces that an ingest finished, since the ingestion layer broadcasts nothing. Every row shows what the database says, so the known defects show through: a book can read "failed" after a retry fixed it (`CLAUDE.md`, "Known Defects"), a scanned PDF "completed" with nothing searchable (#293), and a title the parser got wrong is shown wrong (#86).

**`CakeWeb.ParsedBookLive.Show`** is one document at `/documents/:id`: the same fields, plus its authors, its word count and the number of chunks it was split into (`Cake.Books.count_chunks/1`), as a `list/1`, with the download as the page's primary button. A well-formed id that matches no document is a 404; one that is not a UUID is a 400. There is no create, edit or delete on either page.

**`CakeWeb.Titles`** is how a document's title is displayed in the chat and on the documents pages (the search screen shows the stored title as it is): `display/1` for a stored title, and `display_citation_label/1`, the chat's variant, for a citation's label. Its moduledoc says what each removes and where the two differ. Neither corrects a title the parser got wrong.

**`CakeWeb.BooksController`** serves authenticated book downloads at `/books/download/*file_path`: only keys recorded as a `ParsedBook`'s `source_file_path` that also pass `Cake.Books.Adapters.valid_key?/1` are read back through the configured adapter — the same store `UploadLive` writes to; anything else is reported as not found.

**`CakeWeb.AdminLive`** is the landing page of the admin area at `/admin`, where the top bar's Admin link leads: it names what an admin can manage, which today is the logins, and links to them.

**The admin panel for logins** is three LiveViews under `/admin/users`, inside the admin `live_session`, so every one of them is behind the admin guard. From them an admin creates a login, changes it, sets a new password for it, confirms its email by hand or takes the confirmation back, and removes it:

- **`CakeWeb.Admin.UserLive.Index`**, at `/admin/users`, lists every login in username order: username, email, role, whether the email is confirmed, and created date. "New login" is its primary action, and each row but the admin's own has a Delete button behind a confirmation. On a phone the table keeps the username, the role and Delete.
- **`CakeWeb.Admin.UserLive.Show`**, at `/admin/users/:id`, is one login's page: its fields, and the way to its form and to setting its password. It confirms an unconfirmed login by hand, or takes a confirmation back behind a confirmation dialog (`Cake.Accounts.set_user_confirmed/3`); the admin's own page has neither button, since nobody confirms their own email or takes their own confirmation back. The last confirmed admin's confirmation cannot be taken back either (see "Roles and the First Admin"); their page has the button all the same, and the refusal is a notice.
- **`CakeWeb.Admin.UserLive.Form`** is the forms, one per live action: `:new` at `/admin/users/new` (username, email, password, role; `Cake.Accounts.create_user/1`), `:edit` at `/admin/users/:id/edit` (username, email and role, never the password; `Cake.Accounts.update_user/2`, which leaves the confirmation as it was: the admin vouches for the address they type) and `:password` at `/admin/users/:id/password` (a new password and nothing else; `Cake.Accounts.reset_user_password/2`).

What the panel refuses, it refuses on the page, and setting a password or deleting a login ends that user everywhere at once: the context deletes their sessions and tokens, and the LiveView then calls `CakeWeb.UserAuth.end_live_sessions/1`, which sends their open pages to the log-in page. The three modules' moduledocs carry the rest: which refusal lands on which field, why a typed password never comes back and what a crash report can still print (#399), and how two admins working at once are kept from overwriting each other or acting on a login that is gone.

**`CakeWeb.Router`** is the map of who may open what. The home page is open to everyone. The chat, the documents pages, the search and the upload are one `live_session` (`:authenticated_app`) behind a log-in, so moving between them is a live navigation and not a page load; the download route sits behind the same plug. The admin area is a `live_session` of its own (`:admin`). The account pages are in three more: the ones a logged-in user is turned away from (register, log in, the two password-reset pages), the settings page, which needs a log-in, and the two confirmation pages, open to both. `CakeWeb.UserSessionController` takes the log-in form's POST and the log-out; the settings page's password form posts to the same action with `_action=password_updated`, which logs the user in again after the change and returns them to the settings page. The settings `live_session` also routes `/users/settings/confirm_email/:token`, the link mailed for an email change. In development only, `/dev/dashboard` and `/dev/mailbox` are Phoenix's LiveDashboard and the Swoosh mailbox, where the mails the account pages send can be read.

**`CakeWeb.UserAuth`** provides the authentication plugs (`fetch_current_user/2`, which the `:browser` pipeline runs on every request, `require_authenticated_user/2`, `redirect_if_user_is_authenticated/2` and `require_admin/2`) and the four `on_mount/4` LiveView hooks (`:mount_current_user`, `:ensure_authenticated`, `:redirect_if_user_is_authenticated`, `:ensure_admin`) that the router's `live_session`s use. The `/admin` scope is behind the plug `require_admin/2` and the hook `:ensure_admin`: an admin goes through, a logged-in user who is not one is sent to the home page with a "not authorized" flash, and a visitor who is not logged in is sent to the log-in page. Neither needs the authentication plug or hook before it. Both read the user, and so the role, from the database on each request and each mount, so a demotion takes effect on the user's next navigation. Two more checks cover a page that is already open, which a guard that runs on mount cannot reach: `end_live_sessions/1` sends a user's open pages to the log-in page when an admin sets their password or deletes them, or when the settings page finds its user deleted (a password the user changes or resets themselves deletes their sessions without it), and `:ensure_admin` looks the session up again on every event of a connected admin page (their `@doc`s say how). These `live_session` hooks are the only access check on a LiveView mount (no LiveView declares its own `on_mount`), so they must run on every connected mount; `CakeWeb.LiveJoinAuthorizationTest` pins that a join without a URL cannot skip them.

### The Account Pages

Seven LiveViews. A user logs in with a username. Every user also has an email, and cannot log in until it is confirmed. Each page is a `header/1` and a form in a card, at the shell's default width. Tokens, sessions and hashing are as `mix phx.gen.auth` generates them.

| Page | Module | Route | What it needs |
|---|---|---|---|
| Log in | `CakeWeb.UserLoginLive` | `/users/log_in` | A username and a password. The form posts to `CakeWeb.UserSessionController`, which answers a wrong username and a wrong password alike, and refuses a user whose email is not confirmed, saying so only when the password is right. The page links to the confirmation instructions page. |
| Register | `CakeWeb.UserRegistrationLive` | `/users/register` | A username, an email and a password. It sends the confirmation instructions and sends the visitor to the log-in page; it logs nobody in. A delivery that failed would crash the page with the user already stored: the mail adapter in use cannot fail, and the module's moduledoc says what a release changes. |
| Settings | `CakeWeb.UserSettingsLive` | `/users/settings` | A logged-in user. Shows the username, which this page does not change (an admin's action). Offers changing the email, confirmed by a link mailed to the new address (the link opens this same LiveView at `/users/settings/confirm_email/:token`), and changing the password. |
| Forgot password | `CakeWeb.UserForgotPasswordLive` | `/users/reset_password` | An email. The answer is the same whether or not it matches a user. |
| Reset password | `CakeWeb.UserResetPasswordLive` | `/users/reset_password/:token` | The token from the reset mail. Resetting a password does not confirm the email (#402). |
| Confirmation instructions | `CakeWeb.UserConfirmationInstructionsLive` | `/users/confirm` | An email, answered the same whether or not it matches. |
| Confirm account | `CakeWeb.UserConfirmationLive` | `/users/confirm/:token` | The token from the confirmation mail. |

**Confirmation.** A user who registers is unconfirmed until they follow the mailed link. A user made with `Cake.Accounts.create_user/1` (the first admin, a login an admin hands out, the dev seed's) is confirmed from the start and is sent nothing. Where mail has nowhere to go, as in a release today, an admin confirms a user by hand: `Cake.Accounts.set_user_confirmed/3` confirms a user or takes the confirmation back, for an admin or for `:operator` (the command line), and refuses to take a user's own confirmation back from them (`{:error, :own_account}`) or the last confirmed admin's from anyone (`{:error, :last_confirmed_admin}`; see "Roles and the First Admin"). The gate is at log-in: taking a confirmation back does not end the sessions the user already has (#401). The screen for it is the admin panel's.

**A user deleted meanwhile.** An admin can delete a user who has one of these pages open, or who is half-way through what a page does. No page crashes for it, and each answers as it would a moment later. Log-in answers as for a wrong username or password, so it still says nothing of whether the username existed. The reset and confirmation pages answer as for a link they do not accept, and so does the link mailed for an email change. The settings page, when either form is submitted, sends the user to the log-in page, told that their session has ended: it calls `CakeWeb.UserAuth.end_live_sessions/1`, so the user's other open pages go with it. Registration, should the new account be deleted before its confirmation link is stored, says that the account no longer exists and keeps the form up. The two pages that ask for an email answer as they answer any email: what they say never depended on whom it matched. Underneath, `Cake.Accounts` answers for a user who is gone instead of raising: `delete_user/1`'s `@doc` says how, under "Concurrency".

Nothing closes the self-service pages on a public deployment yet (#367), so all seven are open.

### The App Shell

Every page is rendered inside one shell, `CakeWeb.Layouts.app/1`: a top bar, the page, and the flash messages. The top bar shows the product name (a link home for a visitor, to the chat for a signed-in user), the pages the user may open, the theme toggle, and an account area. What it links to depends on who is looking:

| Viewer | Page links | Account area |
|---|---|---|
| A visitor | none | Register, Log in |
| A member | Chat, Documents, Upload, Search | a menu under the username: Change password (the settings page), Log out |
| An admin | Chat, Documents, Upload, Search, Admin | the same menu |

The links come from the user's role as it was when the page was loaded, and they are only links: the routes are guarded by `CakeWeb.UserAuth` whatever the bar shows. `CakeWeb.Layouts.app/1`'s `@doc` says how a page marks itself as the current one, why its own entry is then not a link, and how the bar collapses on a narrow screen.

**`CakeWeb.PageController`** serves the home page at `/`. A visitor gets the product name, one sentence about it and a log-in button, inside the shell. A signed-in user is redirected to `/chat`, with any flash carried along; log-in itself still lands on `/`, so this is where a user arrives after logging in.

**`CakeWeb.ErrorHTML`** renders the error pages for HTML requests: one page for every status, with the status code, its standard message and a link home. The endpoint renders it inside the root layout (`render_errors` in `config/config.exs`), so it is styled and themed, and outside the shell, because an error can happen before the request has a user or a flash. In development Phoenix's debug page is shown instead. JSON errors are `CakeWeb.ErrorJSON`'s.

### Components, Layouts and Assets

The web layer's kit is the one `mix phx.new` generates on Phoenix 1.8: Tailwind v4 with daisyUI 5, built without Node. `.claude/rules/front-end.md` has the working rules (generator first, daisyUI classes over ad-hoc utilities, where each file comes from and how to update it) and, under "Look and feel", the conventions that keep screens alike. `docs/ui-reference/` holds reference screenshots of the home page, the shell and the search screen in each state, in both themes and at two widths (the member's open menu at phone width only), to put a new screen beside. `docs/demo-script.md` is the path through all of these screens that a presenter or a tester follows, with the limits they will meet on the way.

**`CakeWeb.CoreComponents`** is the generated component library, styled with daisyUI classes: `flash/1`, `button/1`, `input/1`, `header/1`, `table/1`, `list/1` and `icon/1`, the `show/2` and `hide/2` JS commands, and `translate_error/1` and `translate_errors/2`. `use CakeWeb, :html` and `:live_view` import it. Cake adds four components to it: the three state components that every screen uses for the same three situations (`empty_state/1`, `working/1` and `notice/1`), and `status_badge/1` for an ingestion status. Their `@doc`s, and "States" and "Chips and badges" in `.claude/rules/front-end.md`, say when each is used. Three generated components carry an edit beyond their `@spec`s: a `table/1` `:col` may carry a `class`, `header/1` takes one, and `flash/1` sits in the bottom corner (`toast-bottom`).

**`CakeWeb.Layouts`** holds the layouts: `root.html.heex`, the HTML skeleton every page is rendered into, which sets the theme before first paint and the page title ("<page> · Cake" for a page that assigns `page_title`, "Cake" for one that assigns none); `app/1`, the app shell (see "The App Shell" above); `flash_group/1`, which renders the flash messages and the two connection-lost notices as daisyUI toasts; and `theme_toggle/1`, the top bar's system / light / dark switch. Each LiveView and the home page call `app/1` from their own template (`<Layouts.app flash={@flash} current_user={@current_user}>`); `use CakeWeb, :live_view` names no layout.

**Assets.** `assets/css/app.css` is the stylesheet's entry point and the whole Tailwind configuration, the two themes (`light` and `dark`) included. `assets/js/app.js` connects the LiveSocket and the topbar, and hands the LiveSocket the hooks, each a file beside it (`follow_newest.js`, the chat's, is the only one). `mix assets.build` writes `priv/static/assets/css/app.css` and `priv/static/assets/js/app.js`, and `mix assets.deploy` minifies and digests them. Neither needs Node. Where each file comes from, how to update it, and what the kit leaves out while Cake is on LiveView 1.0 are in `.claude/rules/front-end.md`.

### Roles and the First Admin

A user is a `:member` or an `:admin` (`Cake.Accounts.User`'s `role`). Registration always makes a member, whatever the request carries. There is always at least one admin: `Cake.Accounts.update_user_role/2`, `Cake.Accounts.update_user/2` (the admin panel's, which changes the username, the email and the role together) and `Cake.Accounts.delete_user/1` refuse to demote or delete the last one with `{:error, :last_admin}`. They go by the role in the database and are decided one at a time, under one advisory lock (`delete_user/1`'s `@doc` says why, under "Concurrency").

An admin who is not confirmed cannot log in, so there is also always a confirmed admin, once there is one. A demotion or deletion by those three functions, or a confirmation taken back by `Cake.Accounts.set_user_confirmed/3`, that would leave no confirmed admin is refused with `{:error, :last_confirmed_admin}`. `set_user_confirmed/3` refuses it whoever asks, the command line (`:operator`) included. It is decided under the same lock, and each of the four also locks the row of the user it is about, so a confirmation of that user still in flight is seen (the same "Concurrency" section). Taking away the only admin there is stays `{:error, :last_admin}`, and an admin who is not confirmed is not what the rule keeps: they can be demoted or deleted while any other admin remains. The panel shows the refusal where it was asked for: an error on the role in the edit form, a notice on the list and on the login's page. `Cake.Accounts` never refuses a confirmation (the panel refuses an admin their own) and does not take the advisory lock for one, so confirming from the command line is the way back in if no admin is confirmed anyway: `docs/runbooks/first-admin.md` has the command.

**To give someone a login**, an admin uses the panel's "New login" (`/admin/users/new`). No screen can create the first admin, because every admin screen needs an admin: it is created by calling `Cake.Accounts.create_user/1`, with the password kept off the command line. `docs/runbooks/first-admin.md` has both, with the commands for dev and for a release.

The dev seed (`priv/repo/seeds.exs`) creates a dev login, `admin`, as a confirmed admin, and makes it one on a database that was seeded before roles or confirmation existed. Its password is in the repository, and the dev image's `entrypoint.sh` runs the seed on every boot, so that image must never serve anyone but a developer. What keeps the seed out of a release is in `docs/architecture/deployment.md`.
