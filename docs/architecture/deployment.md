# Deployment

The two images, the release's entry points, and what the release-image gate asserts. `README.md` has the domain model and the map of the architecture files.

There are two images, and they are not variants of each other. **`Dockerfile` is the dev image**: `MIX_ENV=dev`, started through `entrypoint.sh`, which waits for OpenSearch to report yellow or green (polling every 5 s, with no timeout), runs `mix deps.get`, recompiles the app and the NIF, creates the database if it is missing and migrates it, runs the seed and starts `mix phx.server`. It is what `docker-compose.yml` builds, and the `compose-smoke` gate covers it (`ci/compose_smoke.sh`, `.claude/rules/compose-smoke.md`). **`Dockerfile.release` is the release image**, the one that is deployed (the first step of staging, #360): a `mix release` built in a builder stage that has Rust for the `parsebooks` crate and builds the assets with `mix assets.deploy`, copied into a runner stage with no Mix, no compiler and no Rust, running as `nobody`. Its build context is filtered by `Dockerfile.release.dockerignore`, which BuildKit prefers over `.dockerignore` when building that file (`.dockerignore` stays the dev image's, which needs `test/` in its context). Both files came from `mix phx.gen.release --docker` and were then edited by hand.

The release has three entry points under `bin/` (each of the first two with a `.bat` twin the generator writes for Windows): `server` (starts the app with `PHX_SERVER=true`), `migrate` (runs `Cake.Release.migrate/0`, which applies every pending migration without starting the app) and `cake` itself (`cake eval`, `cake rpc`, `cake remote`); `Cake.Release.rollback/2` is reached through `cake eval`. `server`, `migrate` and `cake eval` evaluate `config/runtime.exs` first, whose prod block raises unless `DATABASE_URL`, `SECRET_KEY_BASE`, `OPENAI_KEY` and `BOOK_STORAGE_S3_BUCKET` are set, so `bin/migrate` needs the server's environment even though it uses only the database. `cake rpc` and `cake remote` attach to the node that is already running and evaluate no configuration of their own. The release never runs `priv/repo/seeds.exs`: there is no entry point for it, and the image does not contain the file. Nor can a NIF built on a host reach the image: `priv/native` is kept out of the build context and removed in the builder stage before `mix compile` builds the only `parsebooks.so` the release carries.

The `release-image` gate covers this image (`ci/release_smoke.sh`, on every pull request). It builds `Dockerfile.release` and asserts, with one-shot commands in the built image: `bin/cake eval` extracts a fixture PDF through `Cake.ParseBooks.extract_pdf/1` (the fixture is mounted, since the image carries no `test/`), so the NIF compiled in the builder stage loads in the runner stage; `bin/migrate` applies every migration under `priv/repo/migrations` to an empty Postgres; a marker file the script plants in the host's `priv/native` before building does not reach the release, whose `priv/native` holds `parsebooks.so` and nothing else; and no `seeds.exs` is in the release. It does not boot the app. The release cannot boot in prod yet, because of the search node: its address is the one `config/config.exs` sets at build time (`http://opensearch:9200`), and neither `config/prod.exs` nor `config/runtime.exs` has anything for it (#362). The rest is configured at runtime: `config/runtime.exs` reads the object store's bucket, tenant and region and the web endpoint's host, port and secret from the environment.
