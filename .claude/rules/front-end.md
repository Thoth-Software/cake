# Front end

Auto-loaded when working on `assets/`, the components and layouts, a LiveView or a controller template. "Components, Layouts and Assets" in `docs/architecture/web.md` says what each piece is; this says how to work on them.

## The rules

- **Generator first.** The kit is `mix phx.new` output, and a new screen starts from `mix phx.gen.live`, `mix phx.gen.html` or `mix phx.gen.auth` output: run the generator of the Phoenix version `mix.lock` holds (`mix archive.install hex phx_new <that version>`), commit what it wrote unedited, then hand-edit in later commits, so every edit reads as a diff against generator output. A file that cannot sit raw at its real path without breaking a gate goes in a staging directory for that one commit.
- **daisyUI classes over ad-hoc utilities.** Reach for a component class (`btn`, `input`, `alert`, `navbar`, `card`, `table`, `menu`) and a semantic colour (`text-base-content`, `bg-base-100`, `btn-primary`, `text-error`) before spelling one out of Tailwind utilities. Utilities are for layout: spacing, flex, grid, width.
- **No hard-coded palette colours.** `bg-white`, `text-zinc-900` and their kin are right in one theme and unreadable in the other. A colour comes from the theme.
- **No Node.** `mix assets.build` and `mix assets.deploy` run the standalone Tailwind and esbuild binaries and nothing else: no `package.json`, no `node_modules`, no npm package. A JavaScript library is vendored as a file under `assets/vendor/`; a Tailwind plugin is a Mix dependency or a vendored file.
- **Every template calls `Layouts.app` and hands it the user.** A LiveView's `render/1` wraps its content in `<Layouts.app flash={@flash} current_user={@current_user}>`, and so does a controller template (`page_html/home.html.heex`). `use CakeWeb, :live_view` names no layout, so a template that forgets has no top bar and shows no flash; `current_user` is a required attribute, so one that forgets the user does not compile. The error pages are the one exception: `CakeWeb.ErrorHTML` renders inside the root layout and outside the shell, because an error can happen before the request has a user or a flash.
- **Every LiveView sets `page_title`.** The root layout titles a page "<page> · Cake" when `page_title` is assigned and "Cake" when it is not, and it adds the suffix only when the first page it rendered had a title. A LiveView without one would lose the suffix for every page live-navigated to after it. `CakeWeb.ShellTest` lists every page with its title: add a new page there.
- **A page the top bar links to passes `current_page`** (`<Layouts.app ... current_page={:chat}>`), so its own entry is inert. Without it the entry is a link to the page being shown, and following it remounts the LiveView and discards its state. `CakeWeb.ShellTest` checks each such page marks itself.
- **A new page goes in the shell's links in one place**, `nav_links/1` in `layouts.ex` (and `current_page`'s `values:`), and in `CakeWeb.LayoutsTest`, `LayoutsPropertyTest` and `ShellTest`, which pin who sees which link. The links are rendered twice (`#main-nav` for wide screens, `#mobile-nav` for the menu they collapse into), so a link has no `id`: a test selects it by its container and its `href`.
- **A form is `<.form>` with `<.input>`.** The Phoenix 1.7 `simple_form/1` and `error/1` that the 1.8 kit dropped were kept in `CakeWeb.TransitionalComponents` while screens still called them. The chat was the last, and the module is gone: do not bring it back for a new screen.
- **LiveView is 1.0.** The kit is written for `phoenix_live_view ~> 1.2`. What needs the newer one is left out: colocated hooks (the `phoenix-colocated/cake` import in `app.js`), colocated CSS (its import and `@source` in `app.css`) and the `:phoenix_live_view` compiler in `mix.exs`. A hook goes in `assets/js/` and is passed to `LiveSocket` by hand. Bring the three back together when LiveView is bumped.

## Look and feel

Screens are built by different sessions at different times, and they have to look like one product. What keeps them alike is that they share the pieces below and do not restyle them. The reference screenshots in `docs/ui-reference/` show the result: the home page, the shell for a member and for an admin, and the search screen in each of its states, at desktop and phone width, in both themes. Put a new screen beside them before calling it done.

- **Width.** Content goes straight into `Layouts.app`, which renders it into one column. A form or a page of prose uses the default; a table of records or the chat asks for `width={:wide}`. A screen does not set a width of its own.
- **Heading.** One `<.header>` per screen, first in the page. Its `:subtitle` and `:actions` slots hold the line under it and the buttons beside it.
- **Wording.** Headings, buttons and labels are in sentence case ("Account settings", "Set password"), whatever case a generator wrote them in.
- **Buttons.** One primary button per view (`<.button variant="primary">`), for its main action. Secondary actions are `btn btn-ghost` or `btn btn-outline`. A destructive action is `btn btn-error`, behind a confirmation (`data-confirm`).
- **Records and results.** Tabular records (documents, users) are a `<.table>`; one record's fields are a `<.list>`. A column a phone has no room for is hidden there with the column's `class` (`<:col class="hidden sm:table-cell">`), as the documents list does, rather than letting the table scroll sideways. Content results (search hits, candidate documents) are cards, as the search screen does them: `card card-border bg-base-100`, a `card-title`, then the detail.
- **States.** Nothing to show yet is `<.empty_state>`; work under way is `<.working>`; a message that is part of the page is `<.notice>` with its `kind` (`:info`, `:success`, `:warning`, `:error`). Never a one-off spinner, alert or "nothing here" line. `<.flash>` stays the dismissible message after an action. A notice added to the page together with what it is about, inside a region that is already announced, passes `role="note"` so it is not spoken ahead of it (the chat's warning under an answer).
- **Previews.** A preview that opens on hover also opens from the keyboard and by tap: a daisyUI `tooltip` around a focusable element (`tabindex="0"`) that the preview describes (`aria-describedby`, `role="tooltip"`). daisyUI centres a tooltip on what it is around, and a preview centred on a narrow chip runs off the edge of a phone and makes the page scroll sideways. So the row of chips is the positioned ancestor (`relative`) and each tooltip is `static`, with its content at `left-0 max-w-[min(20rem,100%)] translate-x-1/2`, its tail hidden (`after:hidden`) and the open chip ringed instead, as the search screen's page chips and the chat's source chips do. That puts the preview above the whole row, which suits a row of a line or two (the chat's sources). Where the chips can fill many lines (a book's pages on the search screen), add `bottom-auto -mt-2 -translate-y-full`, which opens it just above its own chip's line instead of a screen away. A preview is laid out even while it is hidden, so check the page's width with the chips on it, not only with one open.
- **Chips and badges.** `badge badge-soft` with a semantic colour. A status uses the same colour everywhere: `badge-success` for done, `badge-warning` for under way, `badge-error` for failed, `badge-ghost` for not started. An ingestion status is `<.status_badge status={...}>`, which carries those colours.
- **Icons.** Heroicons outline through `<.icon>`, `size-5` inline with text and `size-10` in an empty state.
- **Secondary text** is `text-base-content/70`, not a grey from the palette.
- **Phone width.** Nothing scrolls sideways at 360px, and the primary action stays reachable. Text the user typed can be one long unbroken word: where a page shows it back, it has to wrap (`wrap-anywhere`), as `empty_state/1` does. The reference phone shots are 390px wide, so check 360px in a browser as well.
- **Test selectors.** Anything a test selects carries an `id`, or a `data-part` inside a component; a test does not select by class or by wording it does not mean to pin. The exception is a class that is the thing being pinned: which icon (`hero-…`), which daisyUI variant (`alert-error`), which width.
- **A shared need becomes a shared component.** A component a second screen will also need goes into `CakeWeb.CoreComponents` once, with a `@doc`, a `@spec` and a test in `CakeWeb.CoreComponentsTest`, and is named on the issue the screens are being built under, so screens being built in parallel use it. A screen does not keep a private copy.

## Traps

- **`<.button class="...">` replaces the classes, it does not add to them.** The 1.8 `button/1` uses its own `btn btn-primary btn-soft` only when the caller passes no `class`. A caller that passes one writes the whole list: `class="btn btn-primary w-full"`.
- **The suite cannot see a style.** The LiveView tests assert on text and structure, so a page that has lost its styling passes them. After a change to a component, a layout or `app.css`, build the assets, load the page in a browser and look at it in both themes (the navbar's toggle, or `data-theme="dark"` on `<html>`).
- **The dev container does not build assets.** In Docker the watchers are off (`config/dev.exs`) and the repo is bind-mounted, so the container serves whatever `priv/static/assets/` the host built. Run `mix assets.build` on the host after pulling a change to `assets/`.
- **A form with `phx-submit` needs an `id` and a `phx-change`,** or credo fails it (`LiveViewFormCanBeRehydrated`): without them LiveView cannot put back what was typed after a reconnect. A form that has no change event and nothing worth recovering says so with `phx-auto-recover="ignore"`, as the search box does.
- **There is no favicon.** Phoenix's was removed and Cake has none yet (README "Roadmap"); the root layout declares an empty icon so browsers do not request `/favicon.ico`.
- **The inline theme script.** `root.html.heex` sets `data-theme` from an inline `<script>` before first paint. A Content-Security-Policy without `'unsafe-inline'` blocks it (#213).

## Where the files come from, and how to update them

| What | From | To update |
|---|---|---|
| `core_components.ex`, `layouts.ex`, `layouts/root.html.heex`, `assets/css/app.css`, `assets/js/app.js`, `assets/vendor/heroicons.js`, `assets/vendor/topbar.js`, `assets/tsconfig.json`, the `config :esbuild` and `config :tailwind` blocks | `mix phx.new cake --no-install` with `phx_new` 1.8.16 | Generate a scratch app outside the repo with the `phx_new` of the new Phoenix version, diff each file against the one here, and carry the generator's changes across by hand. The edits made here are `@spec`s, `header/1`'s `class` attribute, the `class` on a `table/1` column, the root layout's title, `app/1` (the generator's placeholder navbar is replaced by Cake's shell), the theme buttons' `aria-label`s, the flash's position (the bottom corner, `toast-bottom`: at the top it covers the account menu and the menu that opens under it), the flash wording the 1.7 `flash_group/1` had (the "Success!" and "Error!" titles, and the server-error notice's text; `CakeWeb.LayoutsTest` pins both), and the LiveView 1.2 features left out. |
| daisyUI | The Mix dependency `:daisyui` in `mix.exs`: the GitHub repository at a tag, sparse-checked-out to `packages/bundle`, not compiled. `app.css` loads it with `@plugin "daisyui/packages/bundle/daisyui"`. | Change the tag, `mix deps.get`, `mix assets.build`, look at the pages in both themes. |
| The two themes | Two `daisyui-theme` blocks in `app.css`, named `light` and `dark`: the names the theme toggle, the inline theme script and the `dark:` variant use. Their values are copied from two of daisyUI's own themes as the bundle in `deps/daisyui` defines them: `light` is Fantasy, `dark` is Dracula. | To change a theme, replace a block's values with another daisyUI theme's (the `themes` object in `deps/daisyui/packages/bundle/daisyui.js`, or https://daisyui.com/theme-generator/) and keep the name. After moving the daisyUI tag, compare the two blocks with the bundle's `fantasy` and `dracula`. |
| heroicons | The Mix dependency `:heroicons`, the same way. `assets/vendor/heroicons.js` turns its SVGs into `hero-*` classes. | Change the tag, `mix deps.get`, `mix assets.build`. |
| Tailwind and esbuild | Standalone binaries the `:tailwind` and `:esbuild` Hex packages download into `_build/` (`mix assets.setup`), at the `version:` each has in `config/config.exs`. | Change `version:`, `mix assets.setup`, `mix assets.build`. Tailwind is configured in `app.css`; there is no `tailwind.config.js`. |

`:daisyui` and `:heroicons` are Git dependencies. `mix hex.audit` and `mix deps.audit` read Hex packages, so neither covers them: read the release notes when moving a tag.
